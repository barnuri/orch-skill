# Shared subagent rules

A coordinator points each dispatched prompt at this file instead of repeating the rules.
Every node agent follows all of them.

1. Do not run `git commit`, `git push`, `git stash`, `git checkout` or `git reset`. The node implements and tests. The main orchestrator owns repository delivery and follows the target repo's instructions. A node handoff must state the branch, changed files and remaining delivery action.
2. Do not delete with `rm`. Use `trash`.
3. Use `ghx`, never `gh`.
4. Never write under `~/.harness-orch` (the orch home). Change orch state only through `dispatch.ts`
   subcommands, and write your handoff into `$ORCH_NODE_OUT`.
5. Do not restart the dashboard service (`service.ts restart`, `dispatch.ts ui`).
6. Run only the tests of the files you touched. Never run the full suite (`tests/run.ts --full`, `bun run test`, `test-all.ts`): it runs once, in the `final-gate-full` node, after the test speed-up nodes are done. Every test command has a hard 5 minute budget per call. `tests/run.sh --full`, `bun run test:budget` and `test-all.ts` stop themselves at 300 s and exit with code 75 (`PARTIAL: N of M files, run again with --resume`): on exit code 75 run the same command with `--resume` (`bun run test:resume` for bun) until it exits 0 or 1. Never raise the budget. Any other test command is stopped at 5 minutes (`timeout 300`); if it was cut, run only the remaining files. A path-only or doc-only change needs no test run beyond a syntax check.
7. Keep calling tools until the task is done. Do not stop to ask when you can decide.
8. Keep the final report to 6 lines or fewer: what changed, test result, files. Before you report done, run `bun scripts/precommit-smoke.ts` from the repo root (syntax, `dispatch.ts run status`, typecheck; under 20 s) and fix any failure first.
9. You can talk to other nodes and to the coordinator, and the main session (the coordinator) is the messenger. Ask the coordinator with `dispatch.ts node ask <run> $ORCH_NODE_ID "<question>" --wait 90`. Tell another node with `dispatch.ts node tell <run> <other-node> "<text>" --from $ORCH_NODE_ID`: the message goes through the coordinator, which sees it, relays it and can answer or veto it. Read your messages with `dispatch.ts node inbox <run> $ORCH_NODE_ID --unread` before you start and after every large step. When two nodes edit the same file, message the other node before you edit. Never guess when something is missing: ask.
10. Your shell tool times out after about 120 s, so `node ask --wait` must be 90 or less. After a wait with no answer, keep working on what you can, run `node inbox <run> $ORCH_NODE_ID --unread` between steps, and after 3 rounds continue with your best choice and write it in the handoff. Never end a turn waiting for an answer: an ended turn counts as a killed job. Never use the question tool, never ask the user directly, never end a turn with a question in text. All questions go to the coordinator through `dispatch.ts node ask ... --wait 90`. The coordinator answers technical and plan questions itself. When the answer needs the user (a preference, a risk, a cost, credentials, scope), the coordinator asks the user through the question tool and relays the answer with `node answer`. If no answer arrives, state your best choice in the handoff and continue with it.
11. Your task is in `$ORCH_NODE_GOAL` (also written to `$ORCH_NODE_GOAL_FILE`, which is `goal.md` in `$ORCH_NODE_OUT`). Read it before you start. A prompt that only says "see node goal" already has it appended as a `## Your task` section.
12. Before your final response, write a non-empty `$ORCH_NODE_OUT/handoff.md`. If no files changed, write exactly what was verified and why no edit was needed. Chat text, a result record, commit text, or "this message is the handoff" never replaces the file. Right after you write `handoff.md`, record a one-line result: `dispatch.ts node result $ORCH_RUN_ID $ORCH_NODE_ID --verdict full|partial|blocked --summary "<one sentence>" --follow-up "<findings or none>"` (the run and node ids default to your env, so `dispatch.ts node result --verdict ... --summary ... --follow-up ...` works). The line reads `verdict: full|partial|blocked | summary: <one sentence> | follow_up: <findings or none>`. `blocked` needs a summary. Finishing with no result records verdict `unknown` and a warning. A `partial` or `blocked` result with a follow_up other than `none` fails `run verify` until handled. The main session reads `handoff.md` only when the result says partial, blocked or has a follow_up, so put the detail there.
